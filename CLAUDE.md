# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FindHackEU (formerly "Euro Hackathons") is a Next.js 16 (App Router) site that aggregates hackathons happening across Europe. Data is scraped from external sources, stored in Supabase, exposed via a REST API and a filterable web UI, and pushed out through Discord/Telegram/Twitter bots. The pipeline no longer auto-regenerates `README.md` (issue #3) — the README is a normal, manually maintained project document now.

FindHackEU is an independent project, MIT-licensed (see `LICENSE`), originally inspired by and born from HackTrack EU by Lorenzo Palaia. It now has its own architecture, infrastructure, issue tracker, and development direction.

### Local Supabase

The project owns its current infrastructure and does not depend on any earlier project's production Supabase/Vercel/API keys. The repository ships its own schema so a fully local stack is possible:

```bash
npx supabase start        # boots local Postgres/Studio via Docker; first run applies supabase/migrations/*
cp .env.example .env.local  # point NEXT_PUBLIC_SUPABASE_URL etc. at the local instance (see `supabase start` output for keys)
```

- `supabase/config.toml`, `supabase/migrations/20260101000000_init.sql`, `supabase/seed.sql` are checked in — the migrations define the `hackathons` table, its status and moderation fields, the `update_hackathon_statuses()` RPC, an `updated_at` trigger, and the relevant RLS policies. Real data comes from running the pipeline, not from seed data — but `seed.sql` (populated for issue #4, previously intentionally empty) now loads a small set of realistic, clearly-fake sample rows (mixed `hackathons.status`/`moderation_state`/`location_type` values and a few `hackathon_candidates` rows across pending/approved/rejected) on every `npx supabase start` (first run) or `npx supabase db reset`, purely so the public site and `/admin` have something to look at immediately with zero API keys configured. Verified live: `npx supabase db reset` applies every migration plus this seed cleanly against a real local Postgres instance.
- The local anon/service-role JWTs Supabase CLI prints are the same fixed dev keys for every local Supabase project — not secrets, safe to keep in `.env.local`.
- `supabase` is a devDependency (CLI only, not imported in code — it's in `knip.json`'s `ignoreDependencies` for that reason).

### Manually triggering the pipeline

Nothing runs automatically outside a real deployment + cron. To run the pipeline locally against your local Supabase instance:

- `npm run trigger-update` — CLI wrapper (`scripts/trigger-update.mjs`) around `POST /api/update`, reads `CRON_SECRET` from `.env.local` via `@next/env`. Defaults to test mode (no bot notifications, no README/GitHub commit); pass `--live` for a real run, `--url=` to target a non-localhost deployment.
- The sidebar has a dev-only "Aggiorna ora (dev)" button (`components/sidebar.tsx`'s `DevTriggerUpdateButton`, rendered only when `NODE_ENV !== "production"`) that calls `app/api/dev/trigger-update/route.ts`. That route 404s outside development, reads `CRON_SECRET` server-side (never exposed to the client), and always forces `x-test-mode: true` — a stray click must never send real notifications or commit README changes. Use the CLI's `--live` flag, not the button, for a real run.
- Or call the endpoint directly: `curl -X POST http://localhost:3000/api/update -H "Authorization: Bearer $CRON_SECRET" -H "x-test-mode: true"`.

The production cron (`.github/workflows/update.yml`) runs once a day via the deployment's `APP_URL` repository variable. The separate uptime workflow is documented under Monitoring.

## Discovery coverage & data quality roadmap

Discovery coverage and data quality work is largely implemented: pagination, date windows, geographic filtering, multilingual classification, topic extraction, honest per-source status, deduplication, update-existing-rows, six provider parsers, and web-search discovery with moderation are in the current codebase. Verify the relevant code and issue history before starting new coverage work.

- Tracking issue: [#2 (EPIC) Improve hackathon discovery coverage and data quality](https://github.com/viganogabriele/FindHackEU/issues/2)
- Remaining Phase 1/tooling follow-ups: issue #62 (public API cursor/limit pagination — filed as non-blocking), issue #27 (marked accessory/low-priority by the maintainer, not being actively worked).
- LabLab remains disabled because its former JSON endpoint disappeared after a framework migration. The active provider set is Luma, Devfolio, MLH, ETHGlobal, Eventbrite, and Devpost; generic web search is a separate moderated candidate pipeline.
- Before picking up any issue, read it in full — it has file/line context, a proposed approach, a cost tier, and acceptance criteria. Don't re-derive this from scratch, and don't duplicate work already covered by a merged PR above.

### Known structural limits on Luma coverage

Not every "missing" hackathon is a bug. Luma events can be set to `visibility: "private"` by their organizer, which makes them structurally invisible to the public discovery API (`https://api.luma.com/discover/get-paginated-events`) — no amount of pagination-depth or geography fixes will surface those. Verify a suspected coverage gap against the event's own Luma page (`https://api.luma.com/url?url=<slug>`) before assuming it's a parser bug; issue #53 was opened and then closed in the project's history for exactly this reason (a "missing" Zurich hackathon turned out to be a private-visibility event, not a coverage gap).

All development and integrations should target FindHackEU's own Supabase/deployment resources or a local Supabase instance.

## Architecture

### Data pipeline (`app/api/update/route.ts`)

This route is the heart of the system, triggered by an external cron job. It is a linear pipeline, and each stage is wrapped so a failure in one stage doesn't abort the rest:

1. Reset `is_new` flags on all rows in Supabase.
2. Run each enabled parser (`lib/parsers/*`, all extending `BaseParser` from `lib/parsers/base-parser.ts`, implementing `discover()` per the `Provider`/`ProviderResult`/`ParseStatus` contract in `lib/providers/provider.interface.ts`) to fetch `ParsedHackathon[]`. Sources are toggled individually via the `sourceResults` map in the route — LabLab is currently disabled (its site was rewritten to Next.js App Router, removing the JSON endpoint the old parser relied on — see `lib/parsers/lablab-parser.ts`; **not** Cloudflare). The six active sources are Luma, Devfolio, MLH, ETHGlobal, Eventbrite, and Devpost. Each source reports an honest `status: "ok" | "partial" | "failed"` — e.g. Luma pagination truncation degrades a source to `"partial"` rather than silently returning incomplete data as if nothing were wrong.

   **Per-stage drop counts (issue #31, added 2026-09-01):** `ProviderResult`/`DiscoverResult` carry an optional `dropped: { byClassifier?, byDateWindow?, byCountry? }`, populated by each parser at its existing reject points (no new rejection logic, just counting around what already existed). Luma and Eventbrite expose classifier counts because their listing surfaces are not exclusively hackathons; the active providers count applicable date-window and non-European drops. Each parser also logs a one-line per-source summary. `route.ts` copies each provider's `dropped` onto its `sourceResults[name]` entry and the persisted `update_runs.sources` blob. Cross-source duplicate removal is tracked separately as a single aggregate `duplicatesRemoved`.

   **Luma ToS risk (issue #65, accepted 2026-09-01):** `LumaParser` calls `api.luma.com/discover/get-paginated-events`, an unauthenticated internal endpoint that is not Luma's officially supported API (`public-api.luma.com`, which requires a paid Luma Plus subscription with no free tier). This technically conflicts with Luma's own Terms of Service ("you must not access the Service by any means other than our publicly supported interfaces"). The maintainer has consciously accepted this risk for now — it's currently the only source with meaningful European coverage — rather than removing it; see issue #65 before changing this parser's request volume/behavior, and treat any block/contact from Luma as the trigger to reassess, not a bug to route around.

   **Additional providers added 2026-09-01 (issue #10):** Devfolio, MLH, ETHGlobal, Eventbrite, and Devpost use different public listing surfaces and field shapes while following the same provider contract. Coverage from some sources is small — this is expected, not necessarily a parser bug; see each parser's own doc comment for source-specific constraints.
   - **`DevfolioParser`** (`lib/parsers/devfolio-parser.ts`) queries `api.devfolio.co/api/hackathons`. No robots.txt restriction found (unlike Devpost, whose terms explicitly prohibit automated scraping). Skews India-heavy but does surface real European hackathons (verified live, e.g. a Munich, Germany event).
   - **`MlhParser`** (`lib/parsers/mlh-parser.ts`) scrapes the embedded JSON in MLH's own season pages (`mlh.com/seasons/{year}/events`) — `api.mlh.com` itself requires auth on every endpoint tried, so this is the only public surface. MLH's official member-event directory; European share is small (e.g. 1 of 68 upcoming events in a live check) since it's inherently US/Canada-heavy, not a parser bug.
   - **`EthGlobalParser`** (`lib/parsers/ethglobal-parser.ts`) extracts event objects from a Next.js RSC streaming payload on `ethglobal.com/events` via brace-depth matching (no public API, no structured-data script tag on any page) — a fragile source structurally; a site re-render is likely to surface as this source going `"failed"`, which is the intended degradation path. Coverage is sporadic by nature.

   **Fifth source, Eventbrite, added 2026-09-01 (issue #10 follow-up):** `EventbriteParser` (`lib/parsers/eventbrite-parser.ts`) scrapes Eventbrite's public **directory** pages (`eventbrite.com/d/{country}/hackathon/`), a distinct surface from Eventbrite's official Search API (shut down in 2020, already rejected in issue #10 — this is not that). Verified live, 2026-09-01: not blocked by `robots.txt` for this path pattern, and not behind Cloudflare/any bot challenge — a plain fetch with a browser User-Agent gets a normal 200 with server-rendered HTML containing event cards and a `window.__SERVER_DATA__` payload. It follows the payload's pagination with a bounded `EVENTBRITE_MAX_PAGES_PER_COUNTRY` cap (maximum 10) and reports `partial` if Eventbrite advertises pages beyond that bound. It iterates a curated list of 15 European country slugs (`germany`, `france`, `italy`, `spain`, `netherlands`, `united-kingdom`, `poland`, `belgium`, `austria`, `switzerland`, `sweden`, `portugal`, `ireland`, `denmark`, `finland`), mapping each slug to its ISO country code via `europeanCountries.normalizeCountry()` — so, unlike every other parser here, the country is known unambiguously from which page was fetched, not from per-event data. Two things make this parser different from its three HTML-scraping siblings above:
   - **It needs a classifier, like Luma, unlike Devfolio/MLH/ETHGlobal.** Eventbrite's "hackathon" directory category is not exclusively hackathons — real false positives were observed live (e.g. "Build Your First Successful AI SaaS Startup Today! - Workshop", "AI Founder | A to Z... Workshop", "Master AI Entrepreneurship... Masterclass" all appeared in the German listing on 2026-09-01). Every candidate's `name` is run through the same shared `classifyHackathon` Luma uses; only "accepted" survives.
   - **Dates use structured local time when available.** The payload's `start_date`, `start_time`, `timezone`, `end_date`, and `end_time` are converted with the named IANA timezone, including European DST changes; the yearless card text (`"Thu, Nov 12, 5:00 PM"`, `"Today at 1:00 PM + 34 more"`, or `"Thursday at 1:00 PM + 34 more"`) remains a timezone-aware fallback. An unparseable date drops the event rather than guessing, and `aff` tracking parameters are removed from canonical URLs.
   - `location_type` uses structured `is_online_event` when present, recognizes explicit online/virtual cards, and maps an unannounced venue such as `TBD` to `tbd`; only a concrete venue/location is `physical`. `city` comes from the structured primary venue where available, otherwise from the part of `data-event-location="City, ST"` before the comma (the German-federal-state-style suffix after it isn't modeled by this schema).
   - **Sixth source, Devpost, added for issue #5:** `DevpostParser` (`lib/parsers/devpost-parser.ts`) uses Devpost's undocumented public listing endpoint (`devpost.com/api/hackathons`) with `status[]=upcoming|open`, submission-deadline ordering, polite inter-page delay, and a bounded ten-page crawl. The verified response contains listing fields (`title`, `url`, `submission_period_dates`, `themes`, and `displayed_location`) plus pagination counts, but no ISO date/location fields: submission windows are parsed as UTC calendar dates, and `displayed_location` is treated as `City, Country` only when the final segment is an explicitly recognized country. Explicit non-European country codes/names are dropped; online/worldwide listings are retained with `location_type: "online"` and no invented country. Because the endpoint is undocumented and Devpost's terms prohibit automated scraping, this source is inherently fragile and should be reassessed if Devpost contacts the project or changes the listing response.

   Eventbrite, Meetup, Unstop, and 10times were all evaluated and rejected or deprioritized during the same investigation (issue #10) — see that issue's comments for the full verified reasoning before re-proposing any of them. A generic web-search scraper was _not_ rejected — see "Web-search discovery and candidate review" below for how it's implemented (behind a moderation queue, not as a `Provider`).

3. Deduplicate via `lib/dedup/{url-normalizer,fuzzy-matcher,dedupe-hackathons}.ts` — URL normalization (handles `lu.ma`/`luma.com` aliasing) plus fuzzy title+date matching (`areSameHackathon`/`mergeHackathonDuplicates`), not just a `name + date_start` exact composite key.
4. Enhance locations via `LocationEnhancementService` (geocoding), reusing already-known **normalized** URLs from Supabase (paginated fetch, see `fetchAllRows` below) to avoid redundant geocoding calls. Since the public radius filter needs coordinates (issues #109/#118), a new row is geocoded whenever it has a city and either coordinate is missing, even when its source already supplied `country_code`; the known country is included in the lookup address and takes precedence over a conflicting city-only result. A `"not_found"` geocoding outcome leaves the event unresolved rather than dropping it; only an explicitly non-European `country_code` drops an event (see `classifyCountryCode` below).
5. Diff against existing rows in Supabase (matched by normalized URL, falling back to fuzzy same-day matching), insert genuinely new rows, and `update` existing rows whose name/city/country_code/date_start/date_end/topics/notes changed (date/location changes are tracked separately as `notableUpdates` but deliberately **not** wired into notification bots).
6. Call the `update_hackathon_statuses` Postgres RPC to recompute upcoming/past status.
7. If new hackathons were inserted (and not in test mode), fan out notifications to Discord/Telegram/Twitter bots (`lib/bots/*`) via `Promise.allSettled`, then mark rows `notified: true` if at least one channel succeeded.
8. **(Removed, issue #3, 2026-09-02):** the pipeline used to regenerate `README.md`'s hackathon tables via `ReadmeUpdater` and commit them straight to GitHub through the Octokit REST API on every run that changed data. The maintainer no longer wanted the README auto-rewritten with hackathon listings, so this step was deleted outright — `lib/services/readme-updater.ts` and its test are gone (no other caller existed; verified via `grep -rn "readme-updater\|ReadmeUpdater"`), the `@octokit/rest` dependency was removed (it had no other use in the codebase), and `GITHUB_TOKEN` was dropped from `.env.example`/docs since it existed solely for this auto-commit. `dataChanged` is still computed and reported in the route's JSON response (a general "did this run change anything" signal) but no longer drives any README action. `README.md` is now a normal, hand-maintained project document — see it directly rather than this pipeline description.

The route always returns 200/500 with a detailed JSON diagnostic body (per-source `status`/errors, insert/update counts, `updateErrors`, a top-level `degraded` flag, memory usage) rather than throwing — treat every stage's error field as independent, non-fatal state when reading or extending this handler. Auth is fail-closed: a missing `CRON_SECRET` env var returns 500 rather than allowing a literal `"Bearer undefined"` bypass.

**Minimum cooldown between runs (issue #77, added 2026-09-01):** before even creating a `'running'` row, `lib/services/update-cooldown.ts`'s `checkUpdateCooldown()` looks at the single most recent `update_runs` row's `finished_at` (falling back to `started_at` if that run is still in progress or crashed before closing itself out) and compares it against `now`. A request inside `MIN_UPDATE_INTERVAL_MINUTES` (default 5, see `.env.example`; `0` disables the guard) gets a `429` with a structured JSON body (`skipped: true`, `reason: "cooldown"`, `retryAfterSeconds`) instead of starting a new run - a rejected run never creates an `update_runs` row, same as an auth failure. This exists because triggering `/api/update` twice ~2 minutes apart got `EventbriteParser` 429-rate-limited on the second run (2026-09-01) - it's a route-level guard between _separate_ runs, deliberately not a change to `EventbriteParser`'s own intra-run per-country delay. The daily cron (`.github/workflows/update.yml`) runs hours apart and is unaffected in normal operation; any Supabase lookup failure here is treated as "not blocked" (log, don't throw) so this bookkeeping check itself can never prevent a legitimate run.

Every run that gets past auth (and past the cooldown check above) is also persisted to `public.update_runs` (issue #32, migration `supabase/migrations/20260901030000_update_runs.sql`) for history/debugging: a `'running'` row is inserted right after auth succeeds (a rejected/unauthorized request never creates one), and the same row is updated in place — `finished_at`, final `status` (`'success'`/`'failed'`), `sources` (now including each source's `dropped` counts, see issue #31 above), `parsed_count`/`inserted_count`/`updated_count`/`duplicates_removed`, `degraded`, and `error` — at whichever exit point the handler actually takes (the normal end-of-handler response or the outer catch for an unhandled exception). Writing this row is wrapped in its own try/catch that only logs on failure, mirroring the existing `resetError` pattern, so a bookkeeping failure never masks the route's real response.

### Web-search discovery and candidate review (issue #12, #13/#14/#17, added 2026-09-01)

Unlike the six provider sources above, generic web search cannot feed `app/api/update/route.ts`'s `Provider` pipeline directly — a search result is unverified by nature (directory pages, social posts, and stale content routinely rank alongside real event pages; verified live during implementation). Instead:

- `lib/search/search-provider.ts` defines a `SearchProvider` interface with three free-tier implementations (Tavily, SerpAPI, Serper) tried in fallback order via `searchWithFallback` — if one provider's quota is exhausted or it errors, the next is tried, rather than failing the whole query. Configured via `TAVILY_API_KEY`/`SERPAPI_API_KEY`/`SERPER_API_KEY` (all optional individually; see `.env.example`). Brave Search and Google Custom Search were evaluated and rejected — both dropped their free/new-signup tiers by the time of this check.
- `lib/search/extract-event-evidence.ts` fetches a result URL and extracts evidence in preference order: JSON-LD `Event` structured data first (highest confidence), an Open Graph title/description next, the bare `<title>` as a last resort. Returns `null` (not an error) when a page has none of the three — a legitimate "probably not an event page" outcome. `fetchPageHtml`/`extractEvidenceFromHtml` split the fetch from the extraction cascade so `lib/discovery/fetch-classifier.ts` can classify a fetch's outcome before deciding whether to run extraction at all.
- **Conflict detection (issue #15, added 2026-09-01):** when the JSON-LD tier wins, `extractEvidenceFromHtml` also checks the same page's Open Graph title against it; if the two share no meaningful word (a simple, documented word-overlap heuristic — see `titlesConflict` in `extract-event-evidence.ts`), `EventEvidence.has_conflict` is set `true`. This never changes which tier's data is returned — JSON-LD still wins outright — it's purely a signal surfaced as a `has_conflict` column (migration `20260901040000_candidate_has_conflict.sql`) and a destructive `Badge` on `/admin` so a reviewer knows to double-check the page before approving.
- **robots.txt + fetch-outcome classification (issue #16, added 2026-09-01):** before any candidate URL is fetched, `lib/discovery/robots-checker.ts` fetches (and caches per-host, for the lifetime of one `discoverWebCandidates` call) that host's `robots.txt` and checks the path against `User-agent: *` `Disallow`/`Allow` prefix rules only (a deliberately minimal parser — no wildcards, no other named user-agents; a missing/unfetchable robots.txt fails open). `lib/discovery/fetch-classifier.ts`'s `classifyAndFetchPage` is the single entry point that ties this together: robots-check first (never fetches a disallowed URL at all), then classifies the outcome as `"ok" | "blocked-by-robots" | "http-error" | "timeout" | "requires-js"` — the last is a heuristic (little rendered text relative to script-tag size/count) for a JS-only SPA this plain-fetch pipeline can't render, the same "no anti-bot bypass" principle the Luma parser follows. Counts for all four non-`"ok"` outcomes are tracked in `DiscoverCandidatesStats` and printed by `scripts/discover-web-candidates.ts`'s summary.
- `lib/discovery/web-search-candidates.ts` orchestrates queries (a small curated set of European countries × query templates, bounded by `--max-queries`) against the provider chain, runs each new result through `classifyAndFetchPage`, and returns rows for the `hackathon_candidates` table (migration `20260901010000_hackathon_candidates.sql`) — **never** for `hackathons` directly. `lib/discovery/__tests__/candidate-isolation.test.ts` statically proves this: it scans every production `.ts` file under `lib/search/` and `lib/discovery/` and fails if any references the `"hackathons"` table name or imports `lib/parsers/base-parser`.
- **Multilingual/`site:`-scoped query generation (issue #17, added 2026-09-01):** `generateQueries()` builds, per country, up to two English templates (`"hackathon {country} {year}"`, `"student hackathon {country} {year}"`) plus a native-language variant derived from `lib/european-countries.ts`'s existing `EUROPEAN_COUNTRIES[].aliases` data (not a hand-maintained translation table) — `getNativeCountryName()` picks the first alias that isn't just the English name repeated and isn't a short ISO-code-shaped alias (2/3 letters, e.g. `"de"`/`"deu"`), e.g. Germany → `"Deutschland"`, Spain → `"España"`. Some countries (e.g. France, Portugal) have no distinct native alias in the data and get no third query. Once every country's templates are exhausted (or `maxQueries` isn't reached by them), the remaining budget is filled with `"hackathon site:{domain}"` queries against a small, explicitly-curated `SITE_SCOPED_DOMAINS` list of real European university/hackathon-community domains (e.g. `ethz.ch`, `epfl.ch`, `tum.de`) — illustrative, not exhaustive; extend it as more organizer domains are identified. The existing `maxQueries` cap-then-move-to-next-country loop logic is unchanged, just applied to a longer per-country template list.
- **Persistent daily query budget (issue #18, added 2026-09-01):** `lib/discovery/query-budget.ts`'s `QueryBudget` interface (`remaining()`/`recordUsed(n)`) is injected into `discoverWebCandidates` via `DiscoverCandidatesOptions.budget` (optional — omitted in existing tests, which therefore still run unbounded). `FileBudgetTracker` is the real implementation: a small gitignored `.discovery-budget.json` at the repo root tracks `{ date, count, cumulativeCount }`, resetting `count` automatically when the UTC date rolls over; the cap defaults to 30/day, overridable via `DISCOVERY_DAILY_QUERY_BUDGET`. This is deliberately a local JSON file, not a Supabase table — it's operational state about API usage, not application data. `createInMemoryQueryBudget(limit)` is the fake used by tests. `discoverWebCandidates` checks `remaining()` before each query and stops issuing new ones once it hits zero, logging which query index it stopped at and how many were skipped (`DiscoverCandidatesStats.queriesSkippedForBudget`) rather than silently truncating; `scripts/discover-web-candidates.ts` wires up a real `FileBudgetTracker`, prints remaining budget before/after the run, and prints the full generated query list so a non-English/`site:`-scoped query is directly observable in the console.
- `scripts/discover-web-candidates.ts` is the manually-triggered entry point (`npx tsx scripts/discover-web-candidates.ts`), analogous to `trigger-update.mjs` — not part of the daily cron, since search API quota is limited and results need human review regardless of automation.
- `/admin` (dev-only — `notFound()` outside development, same gate as the dev trigger-update button, kept as defense in depth — **and**, as of issue #67, gated behind real Google sign-in via Supabase Auth restricted to a single allowlisted email in `ADMIN_ALLOWED_EMAIL`; see `docs/admin-auth-setup.md` for setup) is the review UI: Pending/Approved/Rejected tabs, "Approve" (or "Approve anyway" on a rejected row, for a false negative) calls `lib/services/promote-candidate.ts`'s `promoteCandidate()`, which is the _only_ path that copies a candidate into the real `hackathons` table — deduped against existing rows via the same `normalizeUrl` identity the main pipeline uses, idempotent against re-approval, and inserted with `status: "estimated"` when no structured date was recoverable (the `estimated` status enum value existed in the schema for exactly this case but had no producer until now). A `has_conflict` candidate shows a destructive warning badge here.
- **Admin auth (issue #67, added 2026-09-01):** `lib/services/require-admin-auth.ts`'s `requireAdminAuth()`/`getAdminAuthStatus()` are the real security boundary — called at the top of every server action in `app/admin/actions.ts` (`approveCandidateAction`, `rejectCandidateAction`, `deleteCandidateAction`, `submitManualCandidateFormAction`) and `app/admin/hackathons/actions.ts` (`deleteHackathonAction`), not just used to hide UI. They check a Supabase Auth session (via `lib/services/supabase-auth-server.ts`'s cookie-aware client) against `ADMIN_ALLOWED_EMAIL`; an unset env var fails closed (denies everyone). The development-only `/admin` dashboard shows a "Sign in with Google" gate (`GoogleSignInButton`, `lib/services/supabase-auth-browser.ts`) when unauthorized, and a "Signed in as {email} · Sign out" element when authorized. `app/auth/callback/route.ts` handles the OAuth code exchange and only allows `/admin` as the post-login destination (`/admin/hackathons` was removed from this allowlist by issue #82, and `/admin/candidates` was removed when the dashboard was later renamed to live at `/admin` directly — see below); `proxy.ts` (this repo's Next 16 proxy) refreshes the Supabase session cookie for `/admin` and `/auth/callback`, propagating Supabase's no-cache headers; public routes are not varied by the auth cookie. The local `supabase/config.toml`'s `[auth.external.google]` reads `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` from env (see `.env.example`) with nonce checking enabled; hosted Supabase redirect URLs must be configured separately as described in `docs/admin-auth-setup.md`. A real Google Cloud OAuth client is a manual per-maintainer setup step that could not be completed or end-to-end-verified in the environment that built this — what could be verified live (the admin page shows the sign-in gate with no session; server actions reject without one) was, and is documented there. The admin page is unavailable when `NODE_ENV=production`, including Vercel Preview deployments.
- **Local no-auth admin bypass (issue #4, added 2026-09-02):** setting up a real Google Cloud OAuth client is unnecessary friction for someone who just cloned the repo and wants to poke at `/admin`/`/admin` locally. `lib/services/require-admin-auth.ts`'s internal `isLocalNoAuthBypassEnabled()` grants every request `authorized: true` (with a synthetic `"local-dev (ADMIN_LOCAL_NO_AUTH)"` display email, not a real session) when either `ADMIN_LOCAL_NO_AUTH=true` is set explicitly, or `GOOGLE_CLIENT_ID`/`ADMIN_ALLOWED_EMAIL` are both left unset (the convenience default — real sign-in couldn't work anyway without them). **This is never reachable in production**: both `getAdminAuthStatus()` and `requireAdminAuth()` call `isLocalNoAuthBypassEnabled()` themselves and it starts with a hardcoded `process.env.NODE_ENV === "production"` short-circuit — every code path that can grant the bypass re-checks this inline rather than trusting an outer gate (the page-level `notFound()` in dev, `requireAdminAuth()`'s own server-action check), so a misconfigured production deploy (env var set, or OAuth vars left empty) cannot trigger it. Verified live in a sandboxed environment with a local Supabase instance already running: with no `GOOGLE_CLIENT_ID`/`ADMIN_ALLOWED_EMAIL` set, `/admin` renders directly with no sign-in gate; setting `ADMIN_ALLOWED_EMAIL` alone restores the real "Sign in with Google" gate; adding `ADMIN_LOCAL_NO_AUTH=true` on top re-enables the bypass. See `.env.example`'s `ADMIN_LOCAL_NO_AUTH` entry and `docs/admin-auth-setup.md`'s "Skip auth entirely for local development" section for the copy-pasteable from-scratch flow (`npx supabase start` → `npx supabase db reset` to load `supabase/seed.sql` → `npm run dev`, no OAuth setup needed).

- **Manual URL submission, delete actions, and explicit topic picking (added 2026-09-01):** `app/admin/manual-submit-form.tsx`'s "Submit a URL manually" dialog (`lib/services/submit-manual-candidate.ts`) lets a signed-in admin hand-enter an event no automated fetch/search can reach (e.g. one only announced via a LinkedIn post, which redirects to a login wall for an unauthenticated fetch — verified live). All fields are controlled React state, not left to the browser's default uncontrolled `<input>` reset-on-every-action-submission behavior, so a validation error no longer wipes what was already typed. The form also includes a toggleable-`Badge` topic picker (`topics text[]` column on `hackathon_candidates`, migration `20260901080000_candidate_topics.sql`) — a submitter who already knows the event can pick its tags explicitly instead of relying solely on `promoteCandidate()`'s title-based `defaultTopicExtractor` fallback, which now only runs when no topics were explicitly chosen. `deleteCandidateAction` (`app/admin/actions.ts`) and `deleteHackathonAction` (`app/admin/hackathons/actions.ts`) both hard-delete via `ConfirmDeleteButton` (`components/confirm-delete-button.tsx`) — distinct from `rejectCandidateAction`, which keeps a rejected row around so a false negative can still be approved later.
- **Published-hackathon management merged into the Approved tab (issue #82, added 2026-09-01):** `/admin/hackathons` used to be a wholly separate page querying the `hackathons` table directly, unrelated to the candidate-review flow. The maintainer's ask ("in approved dovrei trovarli tutti") was that `/admin`'s Approved tab should be where every published hackathon is found and managed — not scoped to just the small minority that came through candidate promotion (`promoted_hackathon_id`), since most published rows come from the main scraping pipeline instead. So `app/admin/page.tsx`'s Approved branch now queries `hackathons` directly (status sub-filter `upcoming`/`past`/`estimated` via an `hstatus` query param, name search, `HackathonCard` + `deleteHackathonAction`) instead of `hackathon_candidates.status = 'approved'` — functionally replacing what `/admin/hackathons` did. `/admin/hackathons` itself is retired as a standalone route: `app/admin/hackathons/page.tsx` is now just a `redirect("/admin?status=approved")` (dev-only gated like before, but no longer auth-gated itself since it reads no session state), while `app/admin/hackathons/actions.ts`'s `deleteHackathonAction` stays in place and is imported by the candidates page. The `/admin` dashboard's "Manage hackathons" card links straight to `/admin?status=approved`. This was a full retirement, not just an unlinking, because a technically-still-reachable-but-unlinked duplicate page is exactly the scattered-admin-surface problem issue #81 was fixing — see the PR for issue #82 for the full reasoning.
- **Unified Pending/Approved/Rejected/Past/Archived moderation model (issue #102, added 2026-09-01):** `hackathons` gained its own `moderation_state` column (`'approved' | 'pending' | 'rejected'`, default `'approved'`, migration `20260901120000_hackathon_moderation_state.sql`) — orthogonal to issue #72's `archived_at`/`archived_reason` (date-based retention only; don't conflate the two). This is what lets an already-published hackathon (most of them — the ones the main pipeline auto-inserted directly, which never had a `hackathon_candidates` row) move back to pending or be rejected without a hard delete, and symmetrically be (re-)approved, via `lib/services/hackathon-moderation.ts`'s `setHackathonModerationState()` and `app/admin/hackathons/actions.ts`'s `setHackathonModerationStateAction`. `hackathon_candidates` and `hackathons` deliberately stay two separate tables — merging them was considered and rejected as much riskier than necessary. `app/api/hackathons/route.ts` now also filters `moderation_state = 'approved'`, alongside the pre-existing `archived_at is null` filter — both are independently required for a row to be public. `/admin`'s Approved tab (issue #82) is now genuinely just "live and not over" — it split into two: **Approved** (`status IN ('upcoming')` or a future-dated `'estimated'`) and **Past** (`status = 'past'` or a past-dated `'estimated'`), both scoped to `moderation_state = 'approved', archived_at IS NULL`; see `app/admin/queries.ts`'s `approvedOrPastHackathonsQuery` for the exact split logic — `"estimated"` (set when a candidate is promoted with no resolved date) is intentionally not its own tab, just a small "Date estimated" badge, per the maintainer's explicit ask. **Pending** and **Rejected** are each now a union of two sources, rendered as two clearly-labeled sections (`hackathon_candidates` rows plus `hackathons` rows in that moderation state) — every query-building function lives in `app/admin/queries.ts`, dependency-injected on the Supabase client specifically so the exact filter/order calls can be unit-tested against a mocked chainable builder (`app/admin/__tests__/queries.test.ts`) without a live database. **Correction to PR #101's original design:** that PR's Archived tab merged archived hackathons with rejected candidates into one view; the maintainer clarified afterward that Rejected (an editorial "no", now also reachable for an already-published hackathon) and Archived (issue #72's purely date-based 1-year retention tier) are separate concepts and must be separate tabs — the Archived tab (`app/admin/queries.ts`'s `archivedHackathonsQuery`) is un-merged back to `hackathons(archived_at is not null)` only, and rejected candidates moved to the (now-unioned) Rejected tab instead. A candidate-sourced Pending/Rejected row keeps using the pre-existing `approveCandidateAction`/`rejectCandidateAction` (issues #78/#93/#94) completely unchanged — the new moderation actions only ever touch `hackathons`, never `hackathon_candidates`.

- **Published-row editing (issue #103, added 2026-09-01):** `lib/services/edit-hackathon.ts` and `app/admin/edit-hackathon-dialog.tsx` let an authenticated maintainer correct a published row's URL, name, date, city/country, and topics in place; the separate service/action path exists because provider-created rows may never have a candidate record. Validation requires a public absolute HTTP(S) URL, a name, and a non-empty date; `hasValidCalendarDate()` rejects impossible calendar dates before the date is converted to ISO, countries are normalized to European codes, and topics are allowlisted. The update sets nullable `manually_edited_at` (`supabase/migrations/20260901130000_manual_hackathon_edits.sql`) and then calls `update_hackathon_statuses`, so a date correction is immediately reclassified as upcoming/past. In `app/api/update/route.ts`'s existing-row diff, `lib/services/hackathon-source-sync.ts` returns no source-update fields once that timestamp is non-null, preserving the complete manually corrected row on later provider runs; this is intentionally row-level because the form submits the complete editable record, not a field-level patch.
- **Structured auto-publish blockers (issue #104, added 2026-09-01):** `lib/discovery/web-search-candidates.ts`'s `AUTO_PUBLISH_BLOCKER_TAGS` and `getAutoPublishBlockers()` use stable `{ code, label }` tags (`non-web-source`, `unstructured-data`, `conflict`, `no-location`, `non-european-location`, `no-date`) instead of prose reasons. `isAutoPublishEligible()` derives from the same blocker list so eligibility and displayed explanations cannot drift; `matchesAutoPublishBlockerFilter()` requires every selected code, while `parseAutoPublishBlockerCodes()` ignores unknown query values and restores canonical tag order. The Pending tab's `PendingReasonFilter` in `app/admin/page.tsx` exposes these tags as a popover checkbox filter, preserving the search query and showing the selected-count badge.
- **LLM-assisted pre-screening suggestions (issue #17, added 2026-09-02):** `lib/services/llm-prescreen.ts`'s `prescreenCandidate()` calls Google's Gemini Flash `generateContent` REST endpoint (`gemini-2.0-flash`, plain `fetch` via `fetchWithRetry`, no SDK — a single call site didn't justify one) directly from `app/admin/page.tsx`'s `PendingTab`, at page-render time, once per visible pending candidate. The prompt (`buildPrescreenPrompt`, tested in isolation) includes the candidate's extracted evidence (`raw_snippet` truncated to 1000 chars, `extraction_method`, `query`, `has_conflict`) and its existing structured auto-publish-blocker tags from `getAutoPublishBlockers()` (issue #104) — reusing signal already computed, not re-deriving it — plus up to 8 recent real approve/reject decisions as few-shot context, pulled via `app/admin/queries.ts`'s `recentCandidateDecisionsQuery()` (`hackathon_candidates` rows with `status IN ('approved','rejected')`, ordered by `reviewed_at desc`, including `reviewer_note` when present — no new data to persist, "reject" was already a reversible soft-state row). Gemini is asked for strict JSON (`{"verdict": "likely-valid"|"caution"|"unclear", "rationale": "..."}`), parsed by `parsePrescreenResponse()` (tolerant of stray markdown code fences).
  This is a **suggestion only**: `PrescreenBadge` renders it as a small badge next to a pending candidate's existing Approve/Reject actions (`AdminTheme`/compact card, same pattern as `AutoPublishBlockers`) — it never calls `promoteCandidate()`/`rejectCandidate()` itself and has no write path at all. Degradation is unconditional: a missing `GEMINI_API_KEY` short-circuits `getPrescreenSuggestions()` before even querying the few-shot examples (no network call, no DB round trip beyond what the Pending tab already does), and every failure mode inside `prescreenCandidate()` — network error, non-2xx response, a 6-second timeout (`DEFAULT_TIMEOUT_MS`), or a response that doesn't parse into the expected shape — resolves to `null` rather than throwing, so the Pending tab renders exactly as it did before this feature whenever Gemini is unconfigured or unavailable. v1 makes one Gemini call per visible pending candidate per page render (no caching) — an accepted tradeoff given the queue's small daily volume (bounded by `DISCOVERY_DAILY_QUERY_BUDGET`, default 30/day); revisit only if page-view or queue volume grows enough to matter.
- **Single admin entry point and compact controls (issues #106/#107, added 2026-09-01):** `app/admin/page.tsx` is the single authenticated, development-only admin landing page: it owns the manual pipeline trigger moved out of the public sidebar and links to the unified `/admin` review/management surface; `/admin/hackathons` remains only the compatibility redirect documented above. `app/admin/page.tsx` uses icon-only action buttons with `title`/`aria-label` affordances and count badges on all five status tabs. `app/admin/queries.ts` supplies count-only variants using exact head queries (`select("id", { count: "exact", head: true })`) so tab badges do not fetch up to 200 rendered rows; list queries retain their ordering/limit separately.
- **Admin dashboard redesign (issues #120/#121, added 2026-09-01):** `app/admin/layout.tsx` wraps all admin pages in a fixed dark, blue-accented `.admin-theme` scope from `app/globals.css`, independent of the public site's selectable theme presets; the `.dark` class is retained inside the wrapper for shadcn dark utilities. The same scope adds the `--success` token used by success action buttons, and mounts the shadcn Sonner `Toaster`; both edit dialogs show a success toast after saves. The compact moderation UI renders one `HackathonCard` per item with `compact`, `meta`, and `titleLink` props, so candidate and published-row cards share the public component while keeping admin metadata and actions dense.

### Data model

- `types/database.ts` — hand-maintained Supabase table types; every schema migration in `supabase/migrations/*.sql` needs a matching manual update here.
- `types/hackathon.ts` — `Hackathon = Database["public"]["Tables"]["hackathons"]["Row"]`.
- Several Supabase calls in `route.ts` carry `@ts-expect-error` because the generated types don't cover `update`/`insert` shapes precisely — this is expected, not a bug to silently "fix" by loosening types elsewhere.
- `lib/supabase.ts` exports two clients: `supabase` (anon key, safe for client-exposed reads) and `supabaseAdmin` (service role key, server-only — used in API routes and scripts).
- Any query that could return more than 1000 rows must go through `lib/services/fetch-all-rows.ts`'s `fetchAllRows<T>()` helper, which pages via `.range()` until a short page — PostgREST silently truncates at `max_rows` (1000) otherwise. `location-enhancement-service.ts`, `scripts/backfill-topics.ts`, and `app/api/update/route.ts`'s existing-row diff all use it; use it for any new bulk read too.
- `location_type` (`"physical" | "online" | "hybrid" | "tbd"`, not null, default `'tbd'`) and `venue` (nullable free text, campus/building detail) were added by issue #21's migration (`supabase/migrations/20260901020000_location_type.sql`) so an online/hybrid/unannounced event doesn't render as blank city/country with no explanation. Each active parser sets `location_type` only from its own source's own explicit signal — never guessed from resolved city/country alone:
  - **Luma**: the raw event payload has an explicit top-level `location_type` field (`"offline"` in every case observed live, 2026-09-01) mapped to `physical`/`online`/`hybrid`; when that field is absent, falls back to `physical` if city/country resolved, else `tbd`. `venue` is not populated (Luma's structured data doesn't carry a distinct campus/building field).
  - **Devfolio**: `is_online: boolean` → `online`/`physical` (no `hybrid` — its `hackathon_setting` field, checked live, is branding/UI config, not a location descriptor).
  - **Devpost**: `displayed_location.icon` (`"globe"`/`"map-marker-alt"` observed live) maps to `online`/`physical`; an explicit online/remote/worldwide/virtual location text also maps to `online`, while missing or unknown physical signals map to `tbd`. Devpost's city/country text is never used to infer `physical`.
  - **MLH**: `formatType` (`"physical" | "digital" | "hybrid_physical"`) maps directly to `physical`/`online`/`hybrid`.
  - **ETHGlobal**: `medium` (`"physical" | "virtual"` observed live) maps `physical`→`physical`, anything else present→`online`, missing→`tbd`.
  - **Eventbrite**: structured `is_online_event: true` or explicit online/virtual location → `online`; an explicit `TBD`/unannounced venue → `tbd`; otherwise a concrete venue/location → `physical`.
  - **LabLab**: disabled (see its own doc comment), sets `tbd` for consistency only — no live effect.
  - A human-approved `hackathon_candidates` promotion (`lib/services/promote-candidate.ts`) always sets `tbd` explicitly — a web-search/manual candidate has no reliable location-type signal.
- `latitude`/`longitude` (`double precision`, nullable) were added by issue #109/#118's `supabase/migrations/20260901140000_hackathon_coordinates.sql`, with database range checks; existing rows remain null until `scripts/backfill-coordinates.ts` is run. That script is dry-run by default, processes sequentially to respect the paid geocoder's quota, and requires `--write` to persist (optionally `--limit=N`).
- `OPENAPI_GEOCODING_KEY` powers both ingestion-time country/coordinate enhancement and the public radius lookup; the latter goes through the rate-limited, one-hour-cached `app/api/geocode/route.ts` proxy so the key is never sent to browser code. `lib/location-filter.ts` calculates great-circle distance with the Haversine formula and rejects rows without valid coordinates while a radius filter is active.
- `lib/services/geocode-cache.ts` persists normalized geocoding queries and coordinates in the `geocode_cache` table (`supabase/migrations/20260901160000_geocode_cache.sql`), with a 180-day TTL and bounded pruning. The geocoding service checks this cache before the primary provider and falls back to Nominatim when the primary provider is unavailable; cache failures are best-effort and do not abort ingestion.
- `preview_image_url` is an optional `hackathons` field (`supabase/migrations/20260901170000_preview_image_url.sql`). Parsers can provide a validated preview URL, ingestion preserves it during synchronization, the public API exposes it, and `components/hackathon-card.tsx` renders it when present.
- `hackathon_candidates` is the moderated queue for web-search and public submissions. `POST /api/submit-hackathon` and `components/public-submit-form.tsx` let anyone suggest an event; `submitManualCandidate()` validates it and applies the shared in-memory IP rate limiter from `lib/http/rate-limit.ts` (10 submissions per hour per client key). It never inserts directly into `hackathons`; an authenticated admin must review it.

### Parsers

New sources implement `BaseParser` (`lib/parsers/base-parser.ts`), returning `ParsedHackathon[]` from a `discover()` method matching the `Provider` interface. The base class provides `formatDate` (tolerant of `"N/A"` and `Z`-suffixed strings, throws on genuinely invalid dates rather than letting `Invalid Date` poison a batch) and `extractTopics` (delegates to `defaultTopicExtractor` in `lib/topic-extractor`, standardizing against `HackathonTopic` from `lib/constants/topics.ts`). Wire a new parser into the pipeline by adding it to `sourceResults` and the parse block in `app/api/update/route.ts`.

`lib/parsers/luma-parser.ts` is the reference implementation: cursor-paginated discovery against `https://api.luma.com/discover/get-paginated-events` across category slugs (`tech`, `ai`, `crypto`), configurable page depth (`LUMA_MAX_PAGES_PER_SLUG` env var), a `hardFailures` counter kept separate from soft pagination-truncation warnings (only real fetch exceptions escalate `status` to `"failed"`), and an explicit non-European drop check via `lib/european-countries.ts`'s `classifyCountryCode(country_code)` — this distinguishes a real-but-non-European code (e.g. `"US"`, correctly dropped) from unrecognized free text (e.g. a US state abbreviation like `"NY"`, which must NOT be treated as a drop signal). That check runs first, unconditionally, against only `geo.country_code`, before any regional/city fallback logic — don't reorder it after the fallbacks or region-name/city-suffix heuristics can produce false-positive non-European drops.

### Classification

`lib/classification/{keywords,hackathon-classifier}.ts` scores candidate events against multilingual (en/it/de/fr+) keyword lists (`AUTO_PUBLISH_THRESHOLD=50`, `BORDERLINE_THRESHOLD=20`). `countMatches` counts **distinct matched substrings** (via `matchAll` + `Set`), not matching pattern count — counting patterns double-counted overlapping cross-language matches (e.g. a German-only event scoring extra points because "Teams" matched both the English `teams?` and German `team(s)?` patterns), which was found via live Luma data and would silently over-publish events with no development activity beyond a shared cognate word.
`lib/detect-non-english.ts` provides the display-only `looksLikeForeignLanguage(text, allowedLocale)` heuristic. It leaves English and ambiguous/multi-language titles visible, and hides a title only when exactly one supported non-English language signal is detected and it differs from the current site locale. The filter is therefore locale-aware rather than English-only; the explicit “include non-English” control can disable it.

### Frontend

- App Router pages under `app/` (`app/docs`, `app/privacy`, `app/terms`, root listing page).
- `app/api/hackathons/route.ts` is the public read API (`GET /api/hackathons?status=upcoming|past`), separate from the write-only `app/api/update` cron endpoint and the dev-only `app/api/dev/trigger-update` endpoint. It exposes a `source` field per hackathon and uses `fetchAllRows` + a `date_start`/`id` sort tie-breaker for stable pagination when no `limit` is given (issue #62, added 2026-09-01: passing `limit` opts into bounded, keyset-paginated responses — `{ data, nextCursor }`, an opaque base64 token over the same `(date_start, id)` sort key — instead of the full dataset; omitting `limit` keeps the exact previous full-list response shape for backward compatibility). Keyset (not offset) pagination was chosen specifically because it stays correct under concurrent inserts, unlike an offset that shifts as new rows land.
- `contexts/filter-context.tsx` holds hackathon filter state (status/location/topics/dates, including an explicit "include non-English" toggle backed by `lib/detect-non-english.ts`); `contexts/translation-context.tsx` drives i18n.
- The public redesign is organized around `components/site-header.tsx`, `components/site-footer.tsx`, and `components/filters-panel.tsx`. `components/hackathon-card.tsx` is shared by the public listing and admin moderation views: it shows validated `preview_image_url` content when available and exposes a bookmark heart.
- `lib/bookmarks-store.ts` provides public bookmarks through a Zustand store persisted in browser `localStorage` under `hacktrack-bookmarks`. Hydration is explicitly deferred until mount, and the listing can filter to “only favorites”; storage failures degrade to a no-op adapter.
- `components/hackathon-map.tsx` is a Leaflet/OpenStreetMap map using marker clustering and the same filtered hackathon data as the listing. `lib/country-centroids.ts` supplies an approximate country-centroid marker when precise coordinates are absent; an empty map falls back to a Europe view.
- `lib/location-filter.ts` supports both exact city selections and country-wide `country:<ISO>` markers in the same flat location array. Selecting a country matches every city in that country; the sidebar then offers the available city values as narrowing selections, without changing the existing exact city behavior (issues #73/#108). The same module owns the radius filter: `components/sidebar.tsx` geocodes the user's place through `/api/geocode`, and `components/hackathon-list.tsx` applies the coordinate-radius test alongside the other client-side filters (issues #109/#118).
- `i18n/*.json` — one JSON file per locale (en, it, de, es, fr, nl, pl, pt, ro, sv). Keep keys in sync across all files when adding new UI strings.
- UI components in `components/ui` follow shadcn/ui conventions (Radix primitives + `class-variance-authority` + `tailwind-merge`).
- **shadcn consistency audit (issue #111, added 2026-09-01):** public-site PR #114 replaced ad-hoc bordered content blocks in `app/docs/page.tsx` and related public controls with the shared `Card`/`Button`/`Badge` primitives; admin PR #119 applied the same variants to topic toggles, tab links/counts, and alert-dialog actions in `app/admin/*` and `components/ui/alert-dialog.tsx`. The point is one token/interaction vocabulary across public and admin surfaces, not a new component system.
- **Admin theme and compact cards (issues #120/#121, added 2026-09-01):** admin styling is intentionally fixed by `.admin-theme` in `app/globals.css` and `app/admin/layout.tsx`; it must not inherit the public theme selector. `components/hackathon-card.tsx` remains the shared card implementation, with `compact`, `meta`, and `titleLink` as the admin-specific layout hooks; `--success` is part of the shared token map so success buttons and status colors remain consistent.
- **Admin navigation and action consistency:** the dashboard and candidate review use one navigation model, shared compact cards, always-visible actions that become disabled when inapplicable, and a consistent button order. `components/copy-link-button.tsx` adds a clipboard action for candidate and published-row URLs.
- Locale/theme hydration: `lib/locale-store.ts`'s Zustand store must never read `localStorage` synchronously during initial-state computation — it starts at a fixed `locale: "en"`, uses `persist({ skipHydration: true })`, and `contexts/translation-context.tsx` calls `useLocaleStore.persist.rehydrate()` inside a `useEffect` post-mount. A prior version read `localStorage` synchronously and caused a real SSR/client hydration mismatch (visible as a flashed wrong-then-right locale/theme) — don't reintroduce that pattern for any other persisted client store. `components/theme-switcher.tsx`'s analogous "has this mounted on the client yet" flag uses `useSyncExternalStore`, not a `useState`+`useEffect` pair (the latter trips `react-hooks/set-state-in-effect`).

### Monitoring (issue #9)

The app exposes `GET /api/health`, a cache-free, side-effect-free 200 response used only to verify that the deployed Next.js app is reachable. `.github/workflows/uptime.yml` calls it every 15 minutes using GitHub Actions and the `APP_URL` repository variable; failures, timeouts, or a missing variable fail the workflow. Sentry (`@sentry/nextjs`) captures errors only when a DSN is configured: there is no analytics, session replay, performance tracing, or default PII collection.

For local dev against a local Supabase instance, `.env.local` only strictly needs `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY` (from `npx supabase start` output) and `CRON_SECRET` (any string you choose) to exercise the pipeline end-to-end; geocoding/bot keys are only needed to test those specific integrations.

### Path aliases

`@/*` maps to the repo root (see `tsconfig.json`), e.g. `@/lib/supabase`, `@/types/hackathon`.

### Dependency version constraints

`eslint-config-next` must track `next`'s exact minor (currently `^16.3.3`/`^16.3.3`); `eslint` is pinned `^9.39.5` (not the `^10.x` that `npm outdated` may suggest) and `typescript` is pinned `^5.9.3` (not `^6.x`) because `typescript-eslint@8.55.0`'s peer range doesn't actually support those newer majors yet — verify with `npm ls` (zero "invalid" warnings) before bumping any of these three together, and re-check `typescript-eslint`'s supported range before ever moving past TS 5.x or ESLint 9.x.

## Working conventions

- Verify subagent and external-review (e.g. Codex) findings against real code and, where possible, real running behavior (local Supabase + a live Luma fetch) before accepting a fix as correct — don't apply a suggested fix on trust, and don't apply the same for your own fixes either. Several real bugs in this repo's history were only caught this way (see the classifier double-counting note above, and the git history around PRs #43/#59 for two more examples).
- Prefer opening focused PRs per issue over one giant change; `main` here has absorbed 20+ merged PRs from parallel work via a consolidation PR pattern (see PR #57) when needed — expect to resolve real merge conflicts when reconciling independently-developed features that touch the same contract (e.g. the `Provider`/`ProviderResult` interface).
