# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HackTrack EU (formerly "Euro Hackathons") is a Next.js 16 (App Router) site that aggregates hackathons happening across Europe. Data is scraped from external sources, stored in Supabase, exposed via a REST API and a filterable web UI, and pushed out through Discord/Telegram/Twitter bots. The public README table is auto-regenerated by the same pipeline.

Original project by Lorenzo Palaia; this is Gabriele Viganò's fork, MIT-licensed (see `LICENSE`). The fork is not expected to be merged upstream — it has diverged significantly (new architecture, its own local dev workflow, its own issue tracker) and is being developed as its own thing, crediting the original author.

There **is** a test suite now: Vitest (`npm run test` / `npx vitest run`), ~53 tests across `lib/**/__tests__/*.test.ts`, covering the classifier, dedup, geo classification, pagination helper, and Luma parser (including regression tests for bugs found via live data — see "Known sharp edges" below). Correctness is still primarily validated via `tsc`/`next build` (type checking), `eslint`, and `knip` (dead code), but run the Vitest suite too before considering discovery-pipeline changes done.

When running lint/knip/vitest from the repo root, scope them to real source directories if stray untracked dirs exist locally (e.g. `.claude/worktrees/*`, `redesign/`) — e.g. `npx eslint app components contexts lib types scripts` — otherwise stale copies in those dirs produce spurious failures. `knip.json` already excludes `.claude`/`redesign` and `vitest.config.mts` should too; if either config is missing those excludes, that's a regression.

### Local Supabase (this fork has no access to the original owner's infra)

Neither the fork's maintainer nor an agent working here has access to the original project's production Supabase/Vercel/API keys — treat that as permanently out of scope, not a gap to route around. The repo now ships its own schema so a fully local stack is possible:

```bash
npx supabase start        # boots local Postgres/Studio via Docker; first run applies supabase/migrations/*
cp .env.example .env.local  # point NEXT_PUBLIC_SUPABASE_URL etc. at the local instance (see `supabase start` output for keys)
```

- `supabase/config.toml`, `supabase/migrations/20260101000000_init.sql`, `supabase/seed.sql` are checked in (they didn't exist before this fork added them) — the migration recreates the `hackathons` table, its `status` check constraint, the `update_hackathon_statuses()` RPC, an `updated_at` trigger, and a public-read RLS policy. `seed.sql` is intentionally empty; real data comes from running the pipeline, not from seed data.
- The local anon/service-role JWTs Supabase CLI prints are the same fixed dev keys for every local Supabase project — not secrets, safe to keep in `.env.local`.
- `supabase` is a devDependency (CLI only, not imported in code — it's in `knip.json`'s `ignoreDependencies` for that reason).

### Manually triggering the pipeline

Nothing runs automatically outside a real deployment + cron. To run the pipeline locally against your local Supabase instance:

- `npm run trigger-update` — CLI wrapper (`scripts/trigger-update.mjs`) around `POST /api/update`, reads `CRON_SECRET` from `.env.local` via `@next/env`. Defaults to test mode (no bot notifications, no README/GitHub commit); pass `--live` for a real run, `--url=` to target a non-localhost deployment.
- The sidebar has a dev-only "Aggiorna ora (dev)" button (`components/sidebar.tsx`'s `DevTriggerUpdateButton`, rendered only when `NODE_ENV !== "production"`) that calls `app/api/dev/trigger-update/route.ts`. That route 404s outside development, reads `CRON_SECRET` server-side (never exposed to the client), and always forces `x-test-mode: true` — a stray click must never send real notifications or commit README changes. Use the CLI's `--live` flag, not the button, for a real run.
- Or call the endpoint directly: `curl -X POST http://localhost:3000/api/update -H "Authorization: Bearer $CRON_SECRET" -H "x-test-mode: true"`.

The production cron (`.github/workflows/update.yml`) currently should run once a day (reduced from 3-5x/day — no need to re-scan that often, and it avoids hammering Luma). If you find it still running on the old schedule or still pointing at a hardcoded upstream Vercel URL instead of an `APP_URL` repo variable, that's a manual edit that couldn't be pushed via `gh` (the CLI's OAuth token lacks `workflow` scope, which blocks pushing to `.github/workflows/*.yml`) — it needs to be pasted through GitHub's web UI by whoever owns the repo settings, not re-attempted via git/gh.

### Known structural limits on Luma coverage

Not every "missing" hackathon is a bug. Luma events can be set to `visibility: "private"` by their organizer, which makes them structurally invisible to the public discovery API (`https://api.luma.com/discover/get-paginated-events`) — no amount of pagination-depth or geography fixes will surface those. Verify a suspected coverage gap against the event's own Luma page (`https://api.luma.com/url?url=<slug>`) before assuming it's a parser bug; issue #53 was opened and then closed in this fork's history for exactly this reason (a "missing" Zurich hackathon turned out to be a private-visibility event, not a coverage gap).

The original repo owner's Supabase, Vercel, and API keys remain out of scope for this fork — every issue that touches the database or an external API is written assuming your own free-tier/local resources.

## Architecture

### Data pipeline (`app/api/update/route.ts`)

This route is the heart of the system, triggered by an external cron job. It is a linear pipeline, and each stage is wrapped so a failure in one stage doesn't abort the rest:

1. Reset `is_new` flags on all rows in Supabase.
2. Run each enabled parser (`lib/parsers/*`, all extending `BaseParser` from `lib/parsers/base-parser.ts`, implementing `discover()` per the `Provider`/`ProviderResult`/`ParseStatus` contract in `lib/providers/provider.interface.ts`) to fetch `ParsedHackathon[]`. Sources are toggled individually via the `sourceResults` map in the route — LabLab is currently disabled (its site was rewritten to Next.js App Router, removing the JSON endpoint the old parser relied on — see `lib/parsers/lablab-parser.ts` and closed issue #11; **not** Cloudflare, contrary to older assumptions); Luma, Devfolio, MLH, and ETHGlobal are the active sources. Each source reports an honest `status: "ok" | "partial" | "failed"` — e.g. Luma pagination truncation degrades a source to `"partial"` rather than silently returning incomplete data as if nothing were wrong.

   **Luma ToS risk (issue #65, accepted 2026-09-01):** `LumaParser` calls `api.luma.com/discover/get-paginated-events`, an unauthenticated internal endpoint that is not Luma's officially supported API (`public-api.luma.com`, which requires a paid Luma Plus subscription with no free tier). This technically conflicts with Luma's own Terms of Service ("you must not access the Service by any means other than our publicly supported interfaces"). The maintainer has consciously accepted this risk for now — it's currently the only source with meaningful European coverage — rather than removing it; see issue #65 before changing this parser's request volume/behavior, and treat any block/contact from Luma as the trigger to reassess, not a bug to route around.

   **Second/third/fourth sources added 2026-09-01 (issue #10):** all three follow the same shape — an undocumented-but-public JSON/embedded-data surface, no auth, structured per-event country data (2-letter ISO codes for MLH/ETHGlobal, matching Luma's shape; full country names for Devfolio, handled with its own explicit-name drop check since `europeanCountries.classifyCountryCode()` is designed for 2-letter codes, not full names). Coverage from each is small — this is expected, not a bug; see each parser's own doc comment for why.
   - **`DevfolioParser`** (`lib/parsers/devfolio-parser.ts`) queries `api.devfolio.co/api/hackathons`. No robots.txt restriction found (unlike Devpost, whose terms explicitly prohibit automated scraping). Skews India-heavy but does surface real European hackathons (verified live, e.g. a Munich, Germany event).
   - **`MlhParser`** (`lib/parsers/mlh-parser.ts`) scrapes the embedded JSON in MLH's own season pages (`mlh.com/seasons/{year}/events`) — `api.mlh.com` itself requires auth on every endpoint tried, so this is the only public surface. MLH's official member-event directory; European share is small (e.g. 1 of 68 upcoming events in a live check) since it's inherently US/Canada-heavy, not a parser bug.
   - **`EthGlobalParser`** (`lib/parsers/ethglobal-parser.ts`) extracts event objects from a Next.js RSC streaming payload on `ethglobal.com/events` via brace-depth matching (no public API, no structured-data script tag on any page) — the most fragile of the four sources structurally; a site re-render is likely to surface as this source going `"failed"`, which is the intended degradation path. Coverage is sporadic by nature (ETHGlobal runs real European events, e.g. Lisbon, periodically, but a given snapshot in time can show zero upcoming ones).

   Eventbrite, Meetup, Unstop, and 10times were all evaluated and rejected or deprioritized during the same investigation (issue #10) — see that issue's comments for the full verified reasoning before re-proposing any of them. A generic web-search scraper was _not_ rejected — see "Web-search discovery and candidate review" below for how it's implemented (behind a moderation queue, not as a `Provider`).

3. Deduplicate via `lib/dedup/{url-normalizer,fuzzy-matcher,dedupe-hackathons}.ts` — URL normalization (handles `lu.ma`/`luma.com` aliasing) plus fuzzy title+date matching (`areSameHackathon`/`mergeHackathonDuplicates`), not just a `name + date_start` exact composite key.
4. Enhance locations via `LocationEnhancementService` (geocoding), reusing already-known **normalized** URLs from Supabase (paginated fetch, see `fetchAllRows` below) to avoid redundant geocoding calls. A `"not_found"` geocoding outcome leaves the event unresolved rather than dropping it; only an explicitly non-European `country_code` drops an event (see `classifyCountryCode` below).
5. Diff against existing rows in Supabase (matched by normalized URL, falling back to fuzzy same-day matching), insert genuinely new rows, and `update` existing rows whose name/city/country_code/date_start/date_end/topics/notes changed (date/location changes are tracked separately as `notableUpdates` but deliberately **not** wired into notification bots).
6. Call the `update_hackathon_statuses` Postgres RPC to recompute upcoming/past status.
7. If new hackathons were inserted (and not in test mode), fan out notifications to Discord/Telegram/Twitter bots (`lib/bots/*`) via `Promise.allSettled`, then mark rows `notified: true` if at least one channel succeeded.
8. If data changed (and not in test mode), regenerate `README.md` via `ReadmeUpdater` (`lib/services/readme-updater.ts`) and commit it straight to GitHub through the Octokit REST API (not a local git operation).

The route always returns 200/500 with a detailed JSON diagnostic body (per-source `status`/errors, insert/update counts, `updateErrors`, a top-level `degraded` flag, memory usage) rather than throwing — treat every stage's error field as independent, non-fatal state when reading or extending this handler. Auth is fail-closed: a missing `CRON_SECRET` env var returns 500 rather than allowing a literal `"Bearer undefined"` bypass.

### Web-search discovery and candidate review (issue #12, #13/#14/#17, added 2026-09-01)

Unlike the four sources above, generic web search cannot feed `app/api/update/route.ts`'s `Provider` pipeline directly — a search result is unverified by nature (directory pages, social posts, and stale content routinely rank alongside real event pages; verified live during implementation). Instead:

- `lib/search/search-provider.ts` defines a `SearchProvider` interface with three free-tier implementations (Tavily, SerpAPI, Serper) tried in fallback order via `searchWithFallback` — if one provider's quota is exhausted or it errors, the next is tried, rather than failing the whole query. Configured via `TAVILY_API_KEY`/`SERPAPI_API_KEY`/`SERPER_API_KEY` (all optional individually; see `.env.example`). Brave Search and Google Custom Search were evaluated and rejected — both dropped their free/new-signup tiers by the time of this check.
- `lib/search/extract-event-evidence.ts` fetches a result URL and extracts evidence in preference order: JSON-LD `Event` structured data first (highest confidence), an Open Graph title/description next, the bare `<title>` as a last resort. Returns `null` (not an error) when a page has none of the three — a legitimate "probably not an event page" outcome.
- `lib/discovery/web-search-candidates.ts` orchestrates queries (a small curated set of European countries × query templates, bounded by `--max-queries`) against the provider chain, extracts evidence for each new result, and returns rows for the `hackathon_candidates` table (migration `20260901010000_hackathon_candidates.sql`) — **never** for `hackathons` directly.
- `scripts/discover-web-candidates.ts` is the manually-triggered entry point (`npx tsx scripts/discover-web-candidates.ts`), analogous to `trigger-update.mjs` — not part of the daily cron, since search API quota is limited and results need human review regardless of automation.
- `/admin/candidates` (dev-only — `notFound()` outside development, same gate as the dev trigger-update button; **no authentication yet**, see issue #67 before ever removing that gate) is the review UI: Pending/Approved/Rejected tabs, "Approve" (or "Approve anyway" on a rejected row, for a false negative) calls `lib/services/promote-candidate.ts`'s `promoteCandidate()`, which is the _only_ path that copies a candidate into the real `hackathons` table — deduped against existing rows via the same `normalizeUrl` identity the main pipeline uses, idempotent against re-approval, and inserted with `status: "estimated"` when no structured date was recoverable (the `estimated` status enum value existed in the schema for exactly this case but had no producer until now).

See `docs/discovery-research.md` for the fuller research behind the "moderation queue, not auto-publish" design decision.

### Data model

- `types/database.ts` — Supabase-generated types (source of truth for table shape).
- `types/hackathon.ts` — `Hackathon = Database["public"]["Tables"]["hackathons"]["Row"]`.
- Several Supabase calls in `route.ts` carry `@ts-expect-error` because the generated types don't cover `update`/`insert` shapes precisely — this is expected, not a bug to silently "fix" by loosening types elsewhere.
- `lib/supabase.ts` exports two clients: `supabase` (anon key, safe for client-exposed reads) and `supabaseAdmin` (service role key, server-only — used in API routes and scripts).
- Any query that could return more than 1000 rows must go through `lib/services/fetch-all-rows.ts`'s `fetchAllRows<T>()` helper, which pages via `.range()` until a short page — PostgREST silently truncates at `max_rows` (1000) otherwise. `readme-updater.ts`, `location-enhancement-service.ts`, `scripts/backfill-topics.ts`, and `app/api/update/route.ts`'s existing-row diff all use it; use it for any new bulk read too.
- `location_type` (`"physical" | "online" | "hybrid" | "tbd"`, not null, default `'tbd'`) and `venue` (nullable free text, campus/building detail) were added by issue #21's migration (`supabase/migrations/20260901020000_location_type.sql`) so an online/hybrid/unannounced event doesn't render as blank city/country with no explanation. Each active parser sets `location_type` only from its own source's own explicit signal — never guessed from resolved city/country alone:
  - **Luma**: the raw event payload has an explicit top-level `location_type` field (`"offline"` in every case observed live, 2026-09-01) mapped to `physical`/`online`/`hybrid`; when that field is absent, falls back to `physical` if city/country resolved, else `tbd`. `venue` is not populated (Luma's structured data doesn't carry a distinct campus/building field).
  - **Devfolio**: `is_online: boolean` → `online`/`physical` (no `hybrid` — its `hackathon_setting` field, checked live, is branding/UI config, not a location descriptor).
  - **MLH**: `formatType` (`"physical" | "digital" | "hybrid_physical"`) maps directly to `physical`/`online`/`hybrid`.
  - **ETHGlobal**: `medium` (`"physical" | "virtual"` observed live) maps `physical`→`physical`, anything else present→`online`, missing→`tbd`.
  - **LabLab**: disabled (see its own doc comment), sets `tbd` for consistency only — no live effect.
  - A human-approved `hackathon_candidates` promotion (`lib/services/promote-candidate.ts`) always sets `tbd` explicitly — a web-search/manual candidate has no reliable location-type signal.

### Parsers

New sources implement `BaseParser` (`lib/parsers/base-parser.ts`), returning `ParsedHackathon[]` from a `discover()` method matching the `Provider` interface. The base class provides `formatDate` (tolerant of `"N/A"` and `Z`-suffixed strings, throws on genuinely invalid dates rather than letting `Invalid Date` poison a batch) and `extractTopics` (delegates to `defaultTopicExtractor` in `lib/topic-extractor`, standardizing against `HackathonTopic` from `lib/constants/topics.ts`). Wire a new parser into the pipeline by adding it to `sourceResults` and the parse block in `app/api/update/route.ts`.

`lib/parsers/luma-parser.ts` is the reference implementation: cursor-paginated discovery against `https://api.luma.com/discover/get-paginated-events` across category slugs (`tech`, `ai`, `crypto`), configurable page depth (`LUMA_MAX_PAGES_PER_SLUG` env var), a `hardFailures` counter kept separate from soft pagination-truncation warnings (only real fetch exceptions escalate `status` to `"failed"`), and an explicit non-European drop check via `lib/european-countries.ts`'s `classifyCountryCode(country_code)` — this distinguishes a real-but-non-European code (e.g. `"US"`, correctly dropped) from unrecognized free text (e.g. a US state abbreviation like `"NY"`, which must NOT be treated as a drop signal). That check runs first, unconditionally, against only `geo.country_code`, before any regional/city fallback logic — don't reorder it after the fallbacks or region-name/city-suffix heuristics can produce false-positive non-European drops.

### Classification

`lib/classification/{keywords,hackathon-classifier}.ts` scores candidate events against multilingual (en/it/de/fr+) keyword lists (`AUTO_PUBLISH_THRESHOLD=50`, `BORDERLINE_THRESHOLD=20`). `countMatches` counts **distinct matched substrings** (via `matchAll` + `Set`), not matching pattern count — counting patterns double-counted overlapping cross-language matches (e.g. a German-only event scoring extra points because "Teams" matched both the English `teams?` and German `team(s)?` patterns), which was found via live Luma data and would silently over-publish events with no development activity beyond a shared cognate word.

### Frontend

- App Router pages under `app/` (`app/docs`, `app/privacy`, `app/terms`, root listing page).
- `app/api/hackathons/route.ts` is the public read API (`GET /api/hackathons?status=upcoming|past`), separate from the write-only `app/api/update` cron endpoint and the dev-only `app/api/dev/trigger-update` endpoint. It exposes a `source` field per hackathon and uses `fetchAllRows` + a `date_start`/`id` sort tie-breaker for stable pagination.
- `contexts/filter-context.tsx` holds hackathon filter state (status/location/topics/dates, including an explicit "include non-English" toggle backed by `lib/detect-non-english.ts`); `contexts/translation-context.tsx` drives i18n.
- `i18n/*.json` — one JSON file per locale (en, it, de, es, fr, nl, pl, pt, ro, sv). Keep keys in sync across all files when adding new UI strings.
- UI components in `components/ui` follow shadcn/ui conventions (Radix primitives + `class-variance-authority` + `tailwind-merge`).
- Locale/theme hydration: `lib/locale-store.ts`'s Zustand store must never read `localStorage` synchronously during initial-state computation — it starts at a fixed `locale: "en"`, uses `persist({ skipHydration: true })`, and `contexts/translation-context.tsx` calls `useLocaleStore.persist.rehydrate()` inside a `useEffect` post-mount. A prior version read `localStorage` synchronously and caused a real SSR/client hydration mismatch (visible as a flashed wrong-then-right locale/theme) — don't reintroduce that pattern for any other persisted client store. `components/theme-switcher.tsx`'s analogous "has this mounted on the client yet" flag uses `useSyncExternalStore`, not a `useState`+`useEffect` pair (the latter trips `react-hooks/set-state-in-effect`).

### Notifications

`lib/bots/{discord,telegram,twitter}-bot.ts` each expose a `notifyNewHackathons(hackathons)` method, invoked together via `Promise.allSettled` so one platform's failure/missing credentials doesn't block the others.

### Dependency version constraints

`eslint-config-next` must track `next`'s exact minor (currently `^16.3.3`/`^16.3.3`); `eslint` is pinned `^9.39.5` (not the `^10.x` that `npm outdated` may suggest) and `typescript` is pinned `^5.9.3` (not `^6.x`) because `typescript-eslint@8.55.0`'s peer range doesn't actually support those newer majors yet — verify with `npm ls` (zero "invalid" warnings) before bumping any of these three together, and re-check `typescript-eslint`'s supported range before ever moving past TS 5.x or ESLint 9.x.

## Working conventions established in this fork

- Verify subagent and external-review (e.g. Codex) findings against real code and, where possible, real running behavior (local Supabase + a live Luma fetch) before accepting a fix as correct — don't apply a suggested fix on trust, and don't apply the same for your own fixes either. Several real bugs in this repo's history were only caught this way (see the classifier double-counting note above, and the git history around PRs #43/#59 for two more examples).
- Prefer opening focused PRs per issue over one giant change; `main` here has absorbed 20+ merged PRs from parallel work via a consolidation PR pattern (see PR #57) when needed — expect to resolve real merge conflicts when reconciling independently-developed features that touch the same contract (e.g. the `Provider`/`ProviderResult` interface).
